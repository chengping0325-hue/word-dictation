## 一、功能 1：静音时朗读有声音

### 1.1 问题现象与根因

iOS 真机上，手机拨到物理静音键后启动听写流程：界面正常走（进度条在动、朗读计数在跳），但**全程没有任何声音，也没有任何错误提示**。用户只会以为 App 卡死了。

根因在 `InnerAudioContext` 的默认行为：iOS 上它**跟随系统静音开关**。安卓 WebView 音频默认不跟随，所以这个问题只在 iOS 暴露——**在开发者工具模拟器里完全测不出来**，属于典型的真机才会暴露的坑。

### 1.2 方案选择

官方文档明确：基础库 2.3.0 起必须用全局 API `wx.setInnerAudioOption`，**实例级 `ctx.obeyMuteSwitch` 已失效**。

但这里有个容易踩空的点——大量流传的教程（包括若干 CSDN 文章）仍在教用实例属性，而且没有说明它在 2.3.0 之后已经不管用了。如果只按旧教程写，新版本客户端上会**看起来配了但没效果**。

最终方案是**两处都设**：

| 位置 | 代码 | 作用 |
|------|------|------|
| `app.js` `onLaunch` | `wx.setInnerAudioOption({ obeyMuteSwitch: false, ... })` | 新版本（≥2.3.0）生效，全局对所有 `InnerAudioContext` 有效 |
| `services/tts-service.js` `playAudio()` | `ctx.obeyMuteSwitch = false`（try/catch 包裹） | 老版本（<2.3.0）唯一可行的方式 |

另外 `wx.setInnerAudioOption` 本身要判空（`if (wx.setInnerAudioOption)`），否则低版本客户端直接抛错。

### 1.3 「与其他音频互斥」是二选一，无法两全

需求要求处理音频互斥。查文档发现微信这里有个硬约束：

> 为保证微信整体体验，`speakerOn` 为 true 时，客户端会忽略 `mixWithOther` 参数的内容，强制与其它音频互斥

也就是说：

| 组合 | 实际行为 | 代价 |
|------|---------|------|
| `speakerOn: true`（扬声器） | **强制互斥** —— 我们的朗读会打断用户正在放的音乐/网课 | 外放声音大，听写场景最清晰 |
| `speakerOn: false`（听筒） | `mixWithOther` 真正生效，**不打断** | 必须插耳机，否则声音很小听不清 |

**没有「外放 + 不打断其他音频」的组合。** 微信为了避免两个音源同时外放听不清，做成了互斥或强制切听筒的取舍。

**决策**：听写场景优先保证声音外放清晰，取 `speakerOn: true`，接受「用户手机正在放音乐时会被短暂打断」。代码里仍写入 `mixWithOther: true`，保留混播意图——若将来微信放开限制就自动生效，无需改代码。

最终配置：

```js
wx.setInnerAudioOption({
  obeyMuteSwitch: false,   // 关键：iOS 静音模式下照常出声
  mixWithOther: true,       // 保留混播意图（当前 speakerOn 为 true 时不生效）
  speakerOn: true           // 走扬声器
})
```

### 1.4 验证方法

1. **iPhone 真机**打开小程序
2. **把侧边物理静音键拨到静音状态**
3. 进入听写流程，确认能听到朗读声

> 开发者工具模拟器无法模拟静音键，这一步**必须在真机上做**。

## 二、功能 2：问题反馈入口及功能

### 2.1 需求形态

用户提出：在主页加「问题反馈」入口 → 点进新页面 → 页面放二维码，**长按可以添加企业微信**。

形态选择上，最初考虑过「表单 + 云数据库 `feedback` 集合」方案（能拿到结构化的设备信息、错误日志）。但最终采用二维码方案，理由：

- 零服务器成本，零外部依赖
- 不收集任何用户信息 → **审核时不需要额外填隐私声明**
- 反馈是低频事件（不是每天几十条）
- 用户可以直接在微信里对话，比填表单更自然

代价是**单向通道**：App 里不留反馈记录，用户加完微信后要自己发消息。这是有意识的取舍。

### 2.2 长按识别二维码：三个必须满足的条件

查官方文档 + 企业微信官方技术支持回复 + 微信服务市场官方 QA，整理出完整条件：

**① 必须显式写 `show-menu-by-longpress="{{true}}"`**

该属性默认值是 `false`。不加的话长按只会弹「保存图片」，完全识别不出码。**这是最容易漏的一步**——页面看着正常，就是长按没反应。

**② 图片路径必须是包内本地路径或合法 HTTPS 地址**

`tempFilePath`（`wx.chooseImage` / `wx.previewImage` / `canvas.toTempFilePath` 的产物）会被小程序运行时安全策略**硬性拦截**，即使设了 `show-menu-by-longpress` 也静默忽略，无法绕过。

本项目用包内路径 `miniprogram/assets/feedback-qrcode.png`，不需要配 request 合法域名，也不用担心图片被 CDN 缓存住换不掉。

**③ 码类型必须在微信官方支持列表内**

| 码类型 | 长按识别 | 最低版本 |
|--------|---------|---------|
| 小程序码 | ✓ | 基础库 2.18.0 |
| 微信个人码 | ✓ | 基础库 2.18.0 |
| 企业微信个人码 | ✓ | 基础库 2.18.0 |
| **企业微信「联系我」二维码** | ✓ | 企业微信官方技术支持确认支持 |
| 企业微信群二维码 | ✓ | |
| 公众号二维码 | ✓ | 仅小程序内嵌公众号文章场景 |
| **微信客服二维码**（`/kfid/`） | **✕** | 官方明确「暂无放开计划」 |
| **第三方活码** | **✕** | |

另有一条版本要求：组件方式（`show-menu-by-longpress`）需 **iOS ≥ 8.0.8 / 安卓 ≥ 8.0.7**，低于此版本长按不弹菜单。本项目 `project.config.json` 的 `libVersion` 是 3.15.2，基础库版本满足。

### 2.3 二维码图片处理：静区是硬要求

原始图片 `319×489`（含上方 logo 头像 + 下方二维码）。处理流程：

```
定位二维码本体 (x 77–241, y 296–460, 165×165)
  → 裁切 + 16px 静区白边 (197×197)
  → LANCZOS 放大到 512×512
  → 8bit 调色板量化
  → 36KB PNG
```

**关键实测结论**：

| 静区留白 | 解码结果 |
|---------|---------|
| 0px（紧贴模块裁切） | **✗ 解码失败** |
| 8px | ✓ 成功 |
| 16px（采用） | ✓ 成功 |

静区（quiet zone）是二维码规范里强制要求的空白边距，贴边裁切会让识别引擎找不到码的边界。**所以以后换码时必须保留四周白边，不能"裁干净"。**

最终图静区实测 41px（16px × 放大倍率 2.6），四边对称。

量化到 8bit 调色板后体积从 132KB 降到 36KB，解码内容与原图**完全一致**（`https://work.weixin.qq.com/u/vcd441622661441a3b?...`）。

### 2.4 `mode="aspectFit"` → `mode="widthFix"`

`aspectFit` 会把图片放进固定尺寸的容器，可能在某些比例下留边或缩放。虽然正方形二维码理论上不变形，但社区反馈里明确提到：

> 坑3：二维码变形识别失败 —— 固定设置 `mode="widthFix"`，禁止固定宽高挤压图片

`widthFix` 让高度按原始比例自适应，**从原理上杜绝了变形可能**。同时移除固定的 `height`，加 `image-rendering: crisp-edges` 避免缩放插值造成的边缘模糊。

### 2.5 兜底路径：为什么是「复制邮箱」而不是「复制微信号」

初版设计的是「复制微信号」按钮。写的时候发现**这条路径本身是无效的**：

用户通过二维码加的是**企业微信**，企业微信用户拿不到你的个人微信号。给一个搜不到的微信号，等于没有兜底。

改成**「复制邮箱」**（`chengping0325@gmail.com`）：

- 与 `docs/PRIVACY.md`、`docs/PRIVACY-PLAIN.txt` 里的邮箱一致
- 是**唯一确定能收到反馈**的渠道
- 文案同步改为「复制后用邮件 App 发给我们」

> 如果后续要用真微信号，改 `pages/feedback/index.js` 里的 `CONTACT_EMAIL` 常量即可，一行的事。

### 2.6 选活码而非静态个人码

用户的码解码出来是 `https://work.weixin.qq.com/u/vcd441622661441a3b?v=...&bb=...`，属于企业微信**「联系我」渠道活码**（`/u/` 是加客户入口，`/kfid/` 才是客服码）。

**活码的好处**：企业微信后台可随时更换接待成员、修改欢迎语，**二维码图片不变，不需要重新发版**。这比静态个人码实用得多——静态个人码一旦员工离职就废了。

跳转与分流由企业微信服务端完成，**不走小程序代码**，所以我们不需要自行解密链接参数。

### 2.7 运营规范注意

微信服务市场官方明确提示：

> 请勿使用利诱等方式诱导用户添加好友或者加入群聊，页面内容需要遵循小程序运营规范，若发现违反规范的行为将封禁识别能力

当前页面文案是中性说明（「遇到问题、想要建议，直接告诉我们」），**不含任何诱导性表述**，符合规范。后续若想加「进群领资料」类文案，需重新评估。

### 2.8 短按二维码刻意不响应

`onTapQrcode` 是空实现。误触短按时若无任何反馈，用户会以为「长按识别坏了」，反而降低长按的使用率。

## 三、页面结构与视觉

### 3.1 入口位置

用户截图标注的位置：**「开始听写」按钮下方、底部 Tab 上方的空白区**。

样式上做成**居中文字链**（图标 + 文字 + 右箭头，`#94a3b8` 弱化色），不抢「开始听写」主按钮的视觉重心。

底部留白同步上调：主页用 `.dictation-index.has-tab-bar`（选择器比 `app.wxss` 的 `.has-tab-bar` 更具体，只影响本页，不影响单词本页）。

### 3.2 导航栏

用**原生导航栏**（`navigationStyle` 默认），标题「问题反馈」，自带返回箭头。理由：它是从主页 `navigateTo` 进来的二级页，原生返回箭头最符合用户直觉，也省掉自绘的维护成本。

对比：`playing` / `finished` / `notebook` 三页用的是 `navigationStyle: custom`（自绘导航栏），因为它们是主流程页需要特殊的深色/沉浸式效果。

### 3.3 布局实现取舍

| 需求 | 实现 | 理由 |
|------|------|------|
| 入口居中 | `display: flex` + `justify-content: center` | 父级是 block 容器。**曾用 `inline-flex` + `margin: auto` 想靠 shrink-to-fit 居中，但 inline 元素在 block 父级下需要父级 `text-align: center` 才居中，不可靠**；也试过 `width: fit-content`，改用 block 级 flex 最稳 |
| 二维码尺寸 | `width: 480rpx` + `mode="widthFix"` | 固定宽高会挤压点阵导致识别失败 |
| 圆角 | **不加** | 圆角会切掉二维码四角，而三个定位角（finder pattern）正是定位的关键，**不能切角** |
| 分享 | 页面级 `onShareAppMessage` | `app.js` 里全局注入了默认分享逻辑，页面自己定义会覆盖它 |

## 四、踩坑记录

### 4.1 编码与工具链

| 坑 | 现象 | 解法 |
|----|------|------|
| **grep 对中文文件失效** | `grep "单词本" docs/02-页面与路由.md` 无输出，但 `grep -c "pages"` 有结果 | 本机 locale 问题。改用 Python 读行内容定位（`grep -c pages` 能中是因为纯 ASCII） |
| **Python 批量改文档多处出错** | replace 后行号漂移导致插入位置错、旧行没删、代码块内多插内容 | 改文档**优先用 Edit 工具**精确匹配；必须用脚本时按行号定位，插入后立即回读校验 |
| **README 插入位置错** | 提示文字插到了 ```` ``` ```` 代码块内部 | 代码块围栏计数校验（`s.count('```') % 2 == 0`），并把提示移到第二个围栏之后 |
| **`width: fit-content` 不可靠** | 二维码容器居中在部分环境偏移 | 改 block 级 flex + `justify-content: center` |
| **校验脚本自身误报** | 把 `<type-tag ... />` 这类自闭合自定义组件报为「标签不配对」 | 脚本需识别自闭合标签 |

### 4.2 微信 API 认知陷阱

| 坑 | 说明 |
|----|------|
| **实例级 `ctx.obeyMuteSwitch` 已失效** | 基础库 2.3.0 起官方改为全局 `wx.setInnerAudioOption`。网上旧教程仍在教实例属性，且不说明失效，新版本上「配了但没效果」 |
| **`show-menu-by-longpress` 默认 false** | 不显式写，长按只弹「保存图片」 |
| **`tempFilePath` 被硬性拦截** | 即使设了 `show-menu-by-longpress` 也静默忽略，无法绕过 |
| **`speakerOn` 会吃掉 `mixWithOther`** | 微信为保证体验强制互斥，没有「外放 + 混播」组合 |
| **活码 vs 死码** | 企业微信官方明确「活码不支持识别，暂无放开计划」。个人码 / 联系我码 / 群码支持，客服码 `/kfid/` 不支持 |

### 4.3 二维码图片处理

| 坑 | 说明 |
|----|------|
| **静区贴边导致解码失败** | 紧贴模块裁切（0px 白边）OpenCV 直接解不出来，留 8px 才成功。**这是规范要求，不是编码问题** |
| **定位本体靠肉眼不可靠** | 用 numpy 逐行统计深色像素占比 + 检测空白行间距来估算模块尺寸，定位到像素级 |
| **量化后必须回读验证** | 8bit 量化有损，不能假设「压缩完还能用」，必须重新解码比对内容 |
